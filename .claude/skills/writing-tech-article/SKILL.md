# Writing a High-Quality Technical Article

## Overview

技術記事は「何を作ったか」の報告書ではなく、「読者が何かを得られる」コンテンツだ。
読者が「読んでよかった」「シェアしたい」と感じるかが唯一の評価基準。

**このスキルを使う前の絶対禁止事項：**
- 読者が誰かを決めずに書き始めること
- 「はじめに」を抽象的なキーワードで書き始めること
- セルフチェックなしで公開すること

---

## Phase 1: リサーチ・設計（書く前に必ず実施）

### 1-A. 3つの問いに答える

記事を書く前に以下を明確にする：

```
1. 誰が読むか？
   （例: TypeScript初心者 / GitHub Actions ユーザー / セキュリティに興味があるエンジニア）

2. 読んで何を得られるか？（1文で）
   （例: GitHub Actions が突然フリーズする原因と AbortController による解決策がわかる）

3. 類似記事と何が違うか？
   （例: 理論でなく、実際に18分フリーズした実体験をベースにしている）
```

これに答えられない記事は書かない。答えが曖昧なら構成を見直す。

### 1-B. 類似記事を3件調査する

Zenn / Qiita で同テーマの記事を検索し、以下を確認する：

- 何が書かれているか（カバー済みのトピック）
- 何が書かれていないか（差別化できる隙間）
- どんな見出し・構成が読まれているか（スキャンして構成を把握）

---

## Phase 2: 構成テンプレート

### 推奨セクション順序

```
## はじめに（フック）
   ★ 具体的なペインシーンから始める（→ 執筆ガイドライン参照）
   - 読者の日常的な課題を行動レベルで描写
   - ペインの結末（疲れた・うまくいかない）
   - このプロジェクト・解決策の一言紹介
   - 完成物 URL・デモへのリンク（あれば）

## 完成物の紹介
   - スクリーンショット・出力例を最初に見せる
   - 「これが作れる」を直感的に伝える

## システム設計・アーキテクチャ
   - 全体像の図（Mermaid 推奨）
   - 技術スタック選定の理由（「なぜ X を選んだか」）
   - MVP として何を削ったか（意思決定の透明性）

## 実装の核心部分
   - 「これが一番重要」というコードを中心に解説
   - コードスニペット必須・コメントで意図を補足
   - 実装上の判断理由（「こうしなかった理由」も有効）

## ハマった罠・トラブルシューティング  ← 最もシェアされやすいセクション
   - 症状（何が起きたか）
   - 調査過程（どう原因を特定したか）
   - 根本原因（なぜ起きたか）
   - 修正（どう直したか）
   - 学び（次に活かせる教訓）

## セキュリティ・品質への取り組み（あれば）
   - Red/Blue Team レビューや TDD など
   - 具体的なコード例付きで

## テスト
   - テスト方針・カバレッジ
   - 印象的なテストケース（タイムアウトのテストなど）

## まとめ・今後の展望
   - 作って気づいたこと（率直な感想）
   - 今後やりたいこと（読者が続きを期待できる内容）
```

## Phase 3: 執筆ガイドライン

### ★ 「はじめに」の書き方（最重要・最も失敗しやすい箇所）

**フックが弱いと読者は離脱する。技術的正確さより共感が先。**

❌ 悪い例（抽象的キーワードから始まる）:
```
英語のテックニュースを毎朝チェックしたいけど、時間がない。

Hacker News のトップには良質な記事が並ぶが、認知コストがかかる。
```
→「時間がない」「認知コスト」は誰でも言える一般論。読者が「自分のことだ」と感じない。

✅ 良い例（具体的な行動シーンから始まる）:
```
朝起きてスマホを手に取ると、気づけば Twitter や Instagram のフィードをダラダラとスクロールしている。
テック系の話題、誰かのホットテイク、広告——何が重要で何がノイズかを判断しながら
読み進めるのは思った以上に消耗する。

Hacker News を開けばトップに良質な記事が並んでいる。ただし英語で。タイトルを読み解き、
「これは読む価値があるか」を判断し、本文をかいつまんで理解する。何本も繰り返すうちに
気づけば 30 分が過ぎ、疲れた割には今日何が起きたかがぼんやりとしか掴めていない。

このキャッチアップ疲れを解決したくて作ったのが tech-digest だ。
```
→ 読者が毎朝やっている具体的な行動（SNS スクロール・英語記事の消耗）から入り、
　 ペインを描き切ってから解決策を提示する。

**フックの3ステップ:**
1. **具体的な行動シーンを描く**（何をしているか・どう感じているか）
2. **ペインの結末を示す**（○分過ぎた・疲れた・うまくいかない）
3. **解決策を提示する**（このプロジェクトはその問題を解決する）

### 「ハマった罠」セクションの書き方

最もシェアされ、最も読まれるセクション。省略しない。

```
【症状】
GitHub Actions の "Run digest" ステップが 18 分以上フリーズし、
タイムアウトなしで無限に待機し続けた。

【調査過程】
ログを見ると extract() の呼び出し後で止まっていた。
Promise.allSettled() でラップしていたが、30 個のうち一部が resolve も reject もしなかった。

【根本原因】
@extractus/article-extractor の extract() にタイムアウト設定がなく、
HTTP 接続がハングしたまま Promise が永遠に pending 状態になっていた。

【修正】
AbortController + setTimeout で 10 秒タイムアウトを実装した。
```

このフォーマットは「他の人が同じ罠にハマったとき検索でたどり着く」記事になる。

### コードスニペットの書き方

- 言語を必ず指定する（```typescript など）
- 関係ない部分は省略して `// ...` を使う
- 重要な行にコメントを付ける
- Before / After で比較すると変化が伝わりやすい

```typescript
// Before: タイムアウトなし（ここが問題）
const result = await extract(url);

// After: AbortController で 10 秒タイムアウト
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 10_000);
try {
  const result = await extract(url, undefined, { signal: controller.signal });
} finally {
  clearTimeout(timer); // タイマー必ずクリア
}
```

### 技術選定理由の書き方

「何を使ったか」だけでなく「なぜ選んだか」「何を捨てたか」を書く。

❌ 悪い例:
```
| AI | Claude Haiku |
```

✅ 良い例:
```
Claude Opus は品質が高いが、毎日自動実行するシステムに使うにはコストが見合わない。
Haiku は Opus の約 1/25 のコスト（2025年3月時点）で、
記事要約という用途なら品質も十分だった。
```

### 文体

- **常体（だ・である調）**で統一する
- 「〜ました」「〜ください」は使わない
- 一文を短く（50字以内を目安）
- 接続詞を多用しない（「また」「そして」の連打は避ける）
- 「〜という」「〜することができる」は削る（「〜できる」で十分）

## Phase 4: セルフチェック（公開前に必ず実施）

### フックチェック（★ 最重要）
- [ ] 「はじめに」が**具体的な行動シーン**で始まっているか（抽象キーワードで始まっていないか）
- [ ] 読者が「これは自分のことだ」と感じられる記述があるか
- [ ] ペインを描き切ってから解決策を提示しているか
- [ ] 完成物・デモへのリンクが「はじめに」内にあるか

### 構成チェック
- [ ] 完成物の出力例・スクリーンショットが序盤にあるか
- [ ] 「ハマった罠」セクションがあるか（最もシェアされる）
- [ ] 技術選定に「なぜ選んだか」の理由が書いてあるか
- [ ] まとめに「作って気づいたこと」という個人的な感想があるか

### コードチェック
- [ ] コードスニペットの言語が指定されているか
- [ ] 掲載コードが実際のリポジトリのコードと一致しているか
- [ ] Before/After の比較が必要な箇所にあるか

### 文体チェック
- [ ] 常体（だ・である調）で統一されているか
- [ ] 一文が長すぎる箇所はないか（50字超を目安に分割）
- [ ] 「〜という」「〜することができる」の冗長表現を削ったか

### 読者視点チェック
- [ ] 「読んで何を得られるか」が記事を読み終えて達成されているか
- [ ] 初見の読者が詰まる専門用語に説明があるか
- [ ] 「今後の展望」で続きを期待させられているか

---

## よくある失敗パターン

| 失敗 | 根本原因 | 対策 |
|---|---|---|
| はじめにが抽象的（「時間がない」「認知コスト」） | 読者シーンを想像していない | 読者の朝・夜・仕事中の具体的行動から書く |
| 実装報告になる（誰が読むか不明） | 読者定義なし | Phase 1-A で「誰が・何を得るか」を先に決める |
| ハマった話がない・薄い | 省いてしまう | 一番シェアされるセクション。必ず書く |
| コードが長すぎて読まれない | 全文掲載の誘惑 | 核心部分だけ抜粋し GitHub リンクで補う |
| 技術選定理由がない | 書き忘れ | 「なぜ X か・なぜ Y でないか」を1文でも書く |
| 常体/敬体が混在する | チェックなし | 公開前に全文を通読して統一する |
| 類似記事との差別化がない | リサーチ不足 | Phase 1-B を必ず実施する |
