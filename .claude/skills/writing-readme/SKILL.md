# Writing a High-Quality README

## Overview

README は「プロジェクトのファーストインプレッション」であり、機能説明書ではない。
読者が「使いたい」と思うか、理解できるかが唯一の評価基準。

**このスキルを使う前の絶対禁止事項：**
- リサーチなしで即書き始めること
- 読者ペルソナを決めずに書くこと
- セルフチェックなしで納品すること

---

## Phase 1: リサーチ（書く前に必ず実施）

### 1-A. 読者ペルソナを決める

README を書く前にユーザーに確認する：

- **ターゲット**: 誰が読むか（エンジニア初心者 / 上級者 / 非エンジニアなど）
- **言語方針**: 日本語のみ / 英語のみ / 英日2言語
- **プロジェクト性質**: 個人利用 / Fork 歓迎 / OSS として貢献も受け付ける

### 1-B. 同カテゴリの有名 OSS README を3件調査する

**書き始める前に**調査する（後付けリサーチは遅い）。WebFetch で raw GitHub URL を取得。

```
調査観点:
1. ファーストビュー（最初の20行）で何を伝えているか
2. セクションの順序と情報設計
3. ビジュアル要素（バッジ・GIF・図）の種類と配置
4. 価値提案の伝え方（問題→解決の対比構造など）
5. セットアップのシンプルさの見せ方
6. このプロジェクトに取り入れるべき要素
```

調査対象の選び方：
- 同じカテゴリ（CLI ツールなら CLI ツール、自動化ツールなら自動化ツール）
- Star 数が多い（1,000以上を目安）
- README の品質で有名なプロジェクト

---

## Phase 2: 設計（書く前に構成を確定する）

### 必須セクションと推奨順序

```
1. ヘッダー（センタリング）
   - タイトル（絵文字 + プロジェクト名）
   - 1行ピッチ（プロジェクトの価値を1〜2文で）
   - バッジ群
   - ライブデモ / 成果物への目立つリンク

2. 言語スイッチャー（2言語対応の場合）
   - ヘッダー直下・右寄せに配置
   ★ 文末ではなく必ずファイル先頭に置く

3. なぜ作ったか / The Problem
   - 読者が「自分のことだ」と感じる具体的なシーンから入る
   ★ 抽象的なキーワードから書かない（→ 執筆ガイドライン参照）

4. 出力例 / Output Example
   - 実際の動作を具体的に見せる（コードブロック）

5. セットアップ / Quick Start
   - 3〜4ステップに凝縮する

6. 仕組み / How It Works  ← 内部仕様なので Quick Start の後に置く
   - Mermaid 図を使うと GitHub で自動レンダリングされる
   ★ ファイル先頭・出力例より前には置かない

7. 技術スタック / Tech Stack

8. セキュリティ / Security（工夫があれば）

9. ローカル開発 / Local Development

10. ライセンス / License
    - Contributing 方針を明示する（受け付ける / 受け付けない）
```

**セクション順序の原則:**
- 「読者の関心が高いもの（Why・What）」を先に
- 「内部実装の詳細（How It Works）」は Quick Start の後
- ライセンス・Contributing は最後

### バッジの選び方

| バッジ種別 | URL パターン | 注意 |
|---|---|---|
| CI ステータス（動的・推奨） | `https://github.com/<owner>/<repo>/actions/workflows/<file>.yml/badge.svg` | 自動更新 |
| License | `https://img.shields.io/badge/license-MIT-blue.svg` | 静的 |
| Node.js バージョン | `https://img.shields.io/badge/node-%3E%3D22-brightgreen.svg` | 静的 |
| テスト数 | **カウントをハードコードしない** → `tests-passing` のみ表示 | 静的数値は将来乖離する |

## Phase 3: 執筆

### ★ 「なぜ作ったか」の書き方（最重要・最も失敗しやすい箇所）

README の最初のセクションは「共感フック」だ。
読者が「これは自分の問題だ」と感じなければ、そこで離脱する。

**書き方の鉄則：抽象→具体の順ではなく、具体的なシーンから書き始める。**

❌ 悪い例（抽象的キーワードから始まる）:
```
英語のテックニュースを毎朝チェックするのは思った以上に認知コストがかかる。
タイトルを読み、重要度を判断し、内容を把握する — これを毎日続けるのは大変だ。
```
→ 「認知コスト」「チェック」は読者が具体的な場面を想像できない。

✅ 良い例（具体的な行動シーンから始まる）:
```
朝起きてスマホを開くと、気づけば Twitter や Instagram のフィードをダラダラとスクロールしている。
テック系の話題、誰かの意見、広告——何が重要で何がノイズかを判断しながら読み進めるのは
思った以上に消耗する。

Hacker News を開けば良質な記事は並んでいる。ただし英語で。タイトルを読み解き、
重要度を判断し、本文をかいつまんで理解する。それを何本も繰り返す。
気づけば 30 分が過ぎ、疲れた割には今日何が起きたかがぼんやりとしか掴めていない。

このキャッチアップ疲れを解決するために作ったのが Tech Digest だ。
```
→ 読者が「あるある」と感じる具体的な行動（Twitter スクロール・英語記事の消耗）から入り、
　 ペインを描き切ってから解決策を提示する。

**共感フックの3ステップ:**
1. **具体的な行動シーンを描く**（何をしているか・どう感じているか）
2. **ペインの結末を示す**（30分過ぎた・疲れた・掴めていない）
3. **解決策を提示する**（このツールはその問題を解決する）

### 価値提案（機能紹介）の書き方

❌ 悪い例（機能の羅列）:
```
- Hacker News API からトップ 50 件を毎朝取得
- Claude Haiku が各記事を 3〜5 文で要約
```

✅ 良い例（ユーザーにとっての変化を書く）:
```
毎朝 1 ページを 2 分で読むだけで済む：
- 毎朝 07:00 JST に Hacker News のトップ 50 件を自動収集
- Claude AI が重要度判定・カテゴリ分類・日本語要約を一括生成
```

### Mermaid 図の設計原則

- データフローは左から右（`flowchart LR`）
- 1ノード1責務（複数の処理をまとめない）
- 最終出力が複数なら**分岐させる**（並列に見えないように注意）
- ノード内改行は `\n`（GitHub Markdown で動作）
- 図が実際のコードのデータフローと一致しているか必ず確認する

### 文体

- **日本語版**: 常体（だ・である調）で統一
- **英語版**: 命令形ベース（Do X, Add Y, Enable Z）
- トーンは「丁寧すぎず、軽すぎず」
- 中点は全角 `・`（半角 `·` は避ける）

## Phase 4: セルフチェック（納品前に必ず実施）

以下を全て確認してから提出する。未確認のまま納品しない。

### フックチェック（★ 最重要）
- [ ] 「なぜ作ったか」が**具体的な行動シーン・場面**で始まっているか（抽象キーワードで始まっていないか）
- [ ] 読者が「これは自分の問題だ」と感じられる記述があるか
- [ ] ペインを描き切ってから解決策を提示しているか（逆順になっていないか）

### ファーストビューチェック
- [ ] 1行ピッチが「このプロジェクトが何か」を1文で伝えているか
- [ ] バッジが正しく表示されるか（URL を手動で確認）
- [ ] ライブデモへのリンクが目立つ位置にあるか
- [ ] 言語スイッチャーがファイル先頭にあるか（文末ではないか）

### 内容チェック
- [ ] "なぜ使うか" が "どう使うか" より先に説明されているか
- [ ] "How It Works" が Quick Start より後に置かれているか
- [ ] Quick Start が 4 ステップ以内に収まっているか
- [ ] Mermaid 図が実際のデータフローを正確に反映しているか
- [ ] テスト数などの静的数値バッジがハードコードされていないか
- [ ] 日英間で内容の矛盾・ズレがないか（2言語の場合）
- [ ] 英語版に日本語テキストが出てくる場合、その旨の説明があるか
- [ ] Contributing 方針が明示されているか

### 技術正確性チェック
- [ ] コマンド例が実際に動作するか
- [ ] モデル名・バージョン・ファイルパスが最新か
- [ ] Mermaid 図のフローが実コードと一致しているか

## よくある失敗パターン

| 失敗 | 根本原因 | 対策 |
|---|---|---|
| フックが抽象的（「認知コストがかかる」など） | 具体的シーンを考えていない | 読者の朝・夜・仕事中の行動を具体的に描く |
| 機能説明の羅列になる | 読者ペルソナ未定義 | Phase 1-A で先に決める |
| How It Works が先頭近くに来る | 情報設計の原則を知らない | セクション順序テンプレートに従う |
| 言語スイッチャーが文末にある | UX を考慮していない | ヘッダー直下・右寄せに配置 |
| バッジがない | GitHub 標準を知らない | Phase 2 のバッジ一覧を参照 |
| 静的数値バッジが古くなる | 手動管理の限界 | テスト数はカウントしない |
| 日英で内容が乖離する | チェックなし | Phase 4 の日英チェックを実施 |
| セットアップが長すぎる | ユーザー視点の欠如 | "3分でできる" を目標に凝縮 |
| リサーチが後付けになる | 着手が早すぎる | 必ず Phase 1 完了後に書き始める |
